# 知识库增量整理与恢复约定

本文描述本地源码中的整理协议。它不表示桌面安装器或云端服务已经更新。

## 输入与依赖

整理链路为：授权后的来源 → 稳定文本块 → 来源共用证据 → 专题编译批次 → 专题页面 → 分组/聚合 → 云事件。来源同步、Wiki、图谱与云端派发由独立工作循环执行，共享的模型队列仍限制总并发。

物理来源 revision 继续用于磁盘一致性和权限核验。自动整理的内容身份另行计算，包含来源 ID、实际文本类型、标题、实际提供给模型的文本，以及语言、处理器和模型身份；不包含文件夹、更新时间、播放路径、标签、API Key 或其他与本次模型输入无关的字段。

整个来源的内容身份只用于判断哪些专题可能受影响。catalog 与来源证据使用文本块自身的身份。`source-layouts/<source-hash>.json` 保存此前的块边界；新文本保留仍存在的旧块作为有序锚点，仅对变化的间隙重新分块，每块不超过 12,000 个字符。头部插入不会平移所有旧块的缓存地址，空的归类结果也属于已完成结果。

## 来源证据与专题编译

`source_analysis` 使用固定的、覆盖所有主题的事实提取任务。相同来源块、语言、模型和处理器只生成一份共用证据。专题目的、人工纠正和专题 ID 不再使同一来源重复提取；这些输入仍参与专题编译身份。

共用证据不是新的独立事实来源。最终 `topic_compile` 继续接收产生证据的完整、有界原文，并根据专题目的筛选、保留不确定性与冲突，引用仍指向原始来源。
即使共用抽取返回空分析，也不据此删除原文块；最终编译器仍可根据原文判断专题是否有足够依据。

`compilation-layouts/<topic-id>.json` 保存专题的批次布局。既有证据批次作为锚点保留，新增证据放入新的有界批次；编辑只使受影响的批次变化。批次缓存身份包含专题指令、模型及该批次各来源块的内容身份和证据，不包含整个专题的来源列表。新增会议不会作废所有旧批次。

## 引用重绑与旧缓存采用

内容身份相同而物理 revision 改变时，缓存引用必须重新绑定到当前 revision，并再次检查来源当前可用、在授权范围内、引用原句仍逐字存在。无效或已经撤销的来源不能通过重绑恢复。失效的录音位置会移除，不能凭旧位置制造新的音频引用。

旧版归类回执按其完整原始输入地址匹配后才能转为块缓存；旧地址中保留物理 revision 的部分也参与匹配。旧页面须匹配完整旧输入指纹、正文哈希和当前有效引用，才可保持页面 ID、审阅和历史并更新缓存身份。不能证明输入相同的旧结果不会被盲目改标签或宣称完成。

服务能力信息中的 `synthesisProfile` 提供处理器版本与默认模型/provider。明确选择模型时，缓存身份使用明确模型和处理器，忽略默认模型和密钥。首次获得服务 profile 建立兼容基线；后续实际模型、provider 或处理器漂移不能继续采用该基线的旧结果。旧服务没有 profile 时保持兼容，但无法识别服务未公开的默认模型变更。

新客户端还会发送本任务绑定的 `expectedSynthesisProfile`。服务在计量步骤开始之前，以及解析实际模型设置之后分别校验；模型或处理器漂移返回明确 409，不调用供应商。客户端清除能力缓存后按新身份继续，避免把另一模型的结果写进旧缓存。

## 模型任务状态与重启

`model-tasks.sqlite` 是持久任务账本，独立于可重建的 `index.sqlite`。其中保存任务输入身份、operation ID、状态、完成输出及重试时间；数据库损坏时停止执行，不自动清空后重发模型请求。

- `queued`：尚未提交，重启后可以继续相同 operation。
- `running`：已经开始提交，进程中断后视为未知结果。
- `done`：输出已经保存，可恢复丢失的次级缓存回执。
- `unknown`：网络结果未知、通用模型 5xx 或响应无法解码，等待明确重试。
- `retryable`：明确的模型 429 或模型提交前的云连接故障，到退避时间后恢复。
- `validation_failed` / `authorization_failed`：保留各自原因，分别由重试或身份/授权恢复路径处理。

同一进程内同一任务使用独立的等待锁，多个专题会等待并复用同一来源证据请求。operation ID 在提交前落盘；新尝试才生成新 ID。HTTP 5xx 不能一律自动重发，因为服务可能已经调用供应商。旧 `jobs.running` 和带未知结果的旧失败会保守迁移为 `unknown`。显式重试释放未知状态，普通心跳和启动不会释放它。

归类和编译的并发波次会保存该波所有成功响应，再报告服务级故障；一个失败响应不会丢掉同波已经完成的成功结果。

## 页面提交与删除

`page-commits/` 是页面提交日志。写正文、引用文件和专题 head 之前先保存提交意图；专题 heads 保存成功后才清除日志。启动读取专题时对未完成提交进行恢复，避免将系统写到一半的正文当作人工修改。

恢复只覆盖仍为旧导出或待提交导出的文件。若中断后出现真正不同的人工 Markdown，保留人工文本，并将待提交页面留在 `recovered/`，不自动覆盖。

专题 heads 和历史正文的分离存储由 `wiki_topic_archive.rs` 管理，兼容旧版内嵌正文，并以内容哈希保存不可变快照。

`topics.json` 保留专题元数据与 `{id, archiveRef}` 修订指针，完整正文/引用/审核/历史保存在专题 `archive/<hash>.json`。按来源倒排生成共同来源边；`wikiRevision` 独立于 `updatedAt`，进度和上传回执变化不触发整库重新读取。同步错误单独保留，不会由 Wiki 完成状态抹掉。引用档案在展开前先过滤删除墓碑，删除中途退出也不会因悬空指针阻断其他专题。

`deleted-topics.json` 保存删除专题及其别名的墓碑。删除顺序是保存墓碑、保存新 heads、再清理页面目录。读取、归类缓存回放和中断提交恢复均不能重新创建这些专题。

## 边界与验证

没有完成的积压任务仍会在重新开启后继续，这是续跑。已完成且输入未变的来源块、分析和编译批次不会因为启动或新同步轮次再次调用模型。模型/语言/处理器实际变化、正文变化和用户明确重新生成仍会产生相应的新任务。

完全未知的远端模型结果不能由客户端凭空恢复；本地保存 operation 和输出能够防止自动重复，但在没有可取回结果的服务协议时，用户明确重试仍可能重新调用供应商。旧服务缺少 profile 时的默认模型漂移同样不可观测。

离线回归覆盖稳定 Unicode 分块、头部插入只新增一个归类任务、旧分块证据复用、并发专题共用一次分析、元数据引用重绑、旧缓存校验采用、未知任务重启保护、429 退避、旧任务 schema 迁移、页面中断恢复、人工编辑保护和专题删除墓碑。不对真实账号发起付费模型请求。
