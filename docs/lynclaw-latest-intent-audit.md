# Lynclaw 最新意图与旧任务边界

检查和修复日期：2026-10-17。适用于全部对话，改名只是其中一种暴露方式。

## 根因

问题不只发生在模型理解层。HTTP 在模型运行前，会从当前会话或卡片令牌恢复旧 pending，并把“确认”等短回复重写为旧操作；此前没有比较当前笔记范围。另有三个兜底会放大旧意图：按“总结/待办”关键词替换用户整句话、数字回复跨多轮寻找旧选项、没有有效 pending 时从历史恢复旧改名。假确认重试还会强制调用发言人管理工具，无论当前问题实际是什么。

长期记忆原有规则已经要求本轮用户指令优先。单加一句提示不能修复上述模型运行前的控制流。

## 通用修复

| 场景 | 当前行为 |
| --- | --- |
| 总结、问答、待办、分组等自由输入 | 保留本轮原话；不因出现旧任务关键词而替换整句，保留否定、范围、语言和其它要求 |
| 新问题替代未处理卡片 | 模型运行前清除旧 pending，撤销 HTTP 卡片令牌及内部准备令牌；包含总结重点和图文选择 |
| 切换笔记 | 核对会话当前笔记、pending 的原笔记和令牌所绑定范围；清除旧目标、进度、会议选项和临时项目/待办焦点 |
| 没有卡片也切换笔记 | 仍重置旧任务焦点；短选项回复不能套用上一篇笔记的菜单 |
| 确认令牌跨进程恢复 | 令牌保留原始笔记范围；恢复后先核对范围，再考虑执行，不能把旧操作迁移到新笔记 |
| 当前话题内追问、修改要求 | 保留历史事实供解释指代；模型按本轮要求判断继续、修改或切换任务 |
| 数字/字母回复 | 仅从最近有效助手回复解析选项，不跳过新问题或新答复寻找更早菜单 |
| “好的”等短回复 | 没有有效 pending 时不从历史重新合成写操作计划 |
| 模型输出了没有准备依据的确认文案 | 重试时重新核对当前意图，按实际操作选准备工具；不再强制改名 |
| 执行器返回失败文字 | 保留已清理的执行结果，避免以通用“已完成”覆盖失败 |

写操作继续要求准备、确认和一次性令牌。此修复不把历史、长期记忆或 AI 自己的旧答复当成新授权。明确恢复某个历史任务时，需要核实当前目标并重新准备。
