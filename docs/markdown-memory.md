# Markdown 共用记忆

## 保存原则

- Lynclaw Memory 是用户长期记忆的主存储，Desktop 和聊天使用同一批记录。身份由经过验证的登录令牌确定，客户端不能选择用户 ID。
- 用户主动新建或纠正的内容显式保存；普通聊天和会议原文不由桌面端无差别写入长期记忆。自动提取沿用 Lynclaw 的授权、来源、分类、候选与确认规则。
- 区分事实、提议、决策与待确认内容。候选记忆可以阅读，在既有确认流程完成前不能通过 Markdown 编辑提升为事实。
- 修改保留原记录的类型、作用域、来源依赖和敏感性。保存通过现有 `MemoryService.apply(replace)` 生成新版本，旧版本标为 superseded，聊天检索使用新记录。
- 云端拒绝、不在线和版本冲突均不能报告为云端保存成功。相同修改使用稳定 operation ID 重试；保存携带云端版本，过期编辑返回 409。
- 遗忘、来源撤销和确认规则由同一个云端服务执行。成功刷新文件列表后移除本机已撤销的干净缓存；有未同步修改的文件保留为冲突草稿，不能重新加入检索。

## Markdown 与云端数据

Markdown 是可编辑的记忆正文。云端沿用现有 PostgreSQL L1 记录保存正文、分类、来源、生命周期和版本，并提供逻辑 `.md` 文件接口；不另外创建一套文件型长期记忆，也不依赖容器的临时文件系统。

- `memory_summary.md`：云端现有有效/候选记忆的只读索引。
- `MEMORY.md`：用户维护的长期笔记；首次保存才建立云端记录。
- `notes/<id>.md`：用户新建的独立记忆，保存到同一批云端 L1 记录。
- `entries/<record-id>.md`：Lynclaw 已有聊天记忆的 Markdown 视图。修改后路径可能随新版本记录 ID 改变。

每条正文沿用云端 8000 字符上限；不保存凭据，敏感内容沿用原服务的作用域和同意门槛。界面里的文件是同一记忆的阅读/编辑表示，分类与权限元数据不靠解析 Markdown 标题推断。

## Desktop 缓存与草稿

本机文件位于 `<vault>/Memory/<scope>/cloud/`。`.cloud-index.json` 保存版本、缓存描述和待同步修改，实际正文同时保存为可阅读的 `.md`。账号隔离标识来自现有验证后的账号和业务服务地址。

在线读取/保存经 Lynclaw `/api/memory/files*` 转发到 Memory `/v1/memory-files*`。同源业务网关需转发 `/api/business/ai/memory/files*`。跨服务地址先验证后端绑定和账号一致性。

- 应用内草稿用客户端状态保存，切换文件/页面保留，退出提醒；退出登录或账号切换清理内存草稿。
- 已缓存文档可离线编辑，显式保存后在本机持久保存待同步项，显示「等待同步」。未缓存的云端内容不伪造为空。
- 打开记忆库、恢复在线或刷新时重试待同步修改。云端冲突/拒绝保留本机版本；「载入已保存版本」经明确操作后才丢弃本机修改。
- 外部修改缓存 Markdown 后，读取时检查并保留修改，进入同样的版本校验与待同步流程。
- 旧版本本机会议条目保留在单独的「旧版会议记忆」中；不自动上传、合并或提升其证据状态。Wiki 发布/审阅流程继续独立运行。

## 接口与交付边界

新接口不改变模型或自动记忆提取策略。Desktop 不直接连接数据库、不持有管理密钥；后端转发使用当前已验证的用户凭据。

新增的 Memory 服务接口和 Lynclaw 代理需要发布后，已安装桌面端才能访问。源码和模拟/离线回归不代表云端接口已经部署，不自动调用真实账号、模型或线上写入。
