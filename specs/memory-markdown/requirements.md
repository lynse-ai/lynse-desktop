# 通用专题记忆与 Markdown 管理

状态：通用专题方案已由用户于 2026-10-24 确认，最终语言规则：所有记忆文件标题统一英文，灵光记的正式英文名称为 lynse；正文和内部章节按实际内容决定语言，不强制任何语言。此规则取代此前“正文默认英文”的要求。灵光记只是项目示例，同一套机制还须适用于课程、重要客户、投资项目、股票、基金等场景，尽量保持通用。代码实现与本机验证已完成；线上部署与桌面发布不在本轮执行范围。

## 问题与目标

用户希望打开一个持续关注的对象或议题，就能看到分散在多次录音中的相关记忆，而无需逐条管理内部记忆状态。此前以“项目”为中心的方案过窄。

建议以“专题”为唯一组织概念：项目、课程、客户、机构、金融标的或跨对象的议题均可成为专题。业务类型可作为可选描述信息，不构成固定栏目、强制模板、权限边界或创建前的必填步骤。

用户故事：作为有多种学习和工作场景的用户，我希望系统从已授权会议总结中识别持续关注的对象与议题，整理为可管理的 Markdown 记忆，并在后续相关会议中持续补充与修正，使我无需预先选择行业分类或维护大量零散条目。

## 核心组织规则

1. **先有专题，再按需拆分。** 一个专题默认一份 Markdown；少量内容不创建目录和空模板。内容积累到有清晰独立子主题时，可逐步拆为目录与文件，并允许用户调整。所有拆分保留内容和引用。
2. **名称来自内容。** 专题名称、别名与小节应依据会议总结中的语境识别。灵光记、课程、客户、股票等均不硬编码；业务类型只帮助理解内容，不限制可接受场景。
3. **专题与事件有区别。** 专题是持续积累的内容单元；事件是某次评审、课堂、客户拜访或调研等具体发生的记录。事件按相关片段关联到一个或多个专题，不因录音不同而自动复制一整篇总结。
4. **身份与名称分离。** 名称相同不足以合并。已有专题的复用需要新旧来源支持对应关系；可利用资料中明确的组织、课程提供方、客户主体、股票或基金代码等区分信息，不依靠外部猜测。别名、重命名和移动不改变同一专题的身份。
5. **持续更新并保留时间。** 新会议补充已有专题，重复信息去重；发生变化时保留“何时、来自哪里”的依据。已知事实、他人观点、讨论、提议和已决定的事项须区分；过往状态不能被无依据地写成当前状态。
6. **人工修正持续有效。** 用户对专题命名、合并/拆分、归属和正文的修正应被后续整理沿用；自动更新不覆盖未处理的人工修改或并发草稿。
7. **克制创建。** 偶然提及的名字不必生成新专题；同一录音也不必独占一个文件。只有具备可积累信息的对象或议题才形成记忆。不确定归属的内容可暂留待整理，用户可纠正；不强行创建“项目”。

## 跨场景示例

以下仅说明通用性，不代表真实会议中已有这些信息，也不要求实际生成这些栏目。

| 专题名称示例 | 可由内容自然形成的小节 |
| --- | --- |
| 灵光记 | 产品方向、硬件研发、评审进展 |
| 某门课程 | 核心概念、学习进度、未解决问题 |
| 某重要客户 | 已知需求、沟通进展、后续事项 |
| 某投资项目 | 业务情况、调研发现、待核实问题 |
| 某只股票 | 经营变化、调研记录、观点变化 |
| 某只基金 | 策略说明、阶段信息、沟通记录 |

用户初次看到的可以只是：

```text
记忆
  lynse.md
  Course Notes.md
  Client Notes.md
  Investment Review.md
  Stock Research.md
  Fund Review.md
```

当某个专题内容明显增多时，再按实际内容拆分，例如：

```text
lynse/
  Overview.md
  Hardware Development.md
  Prototype Review.md
```

不预建“项目/课程/客户/股票/基金”五套目录或模板。没有明确对象的持续议题也可独立为专题；专题之间通过轻量 Markdown 链接关联，用户无需管理复杂图谱。

## 内容语言与文件标题

- 自动生成的记忆正文及内部章节按实际来源内容与语境决定语言，可中文、英文或自然混合，不强制英文或其他语言，也不因界面语言直接翻译。所有记忆文件标题统一英文，包括新建和重命名；界面继续遵循当前设置。
- 文件标题优先使用资料或用户明确提供的正式英文名，没有时使用罗马化名称，不编造品牌译名。用户已明确“灵光记 = lynse”，示例文件使用 lynse.md；中文原名作为别名保留。正文中的人名、组织名、产品名及代码等专名和来源引文仍保留原文。
- 原始会议总结、转写及逐字引用保留原文。英文整理不能替换原文证据，不能把译文当作逐字引文校验。
- 用户可以用中文或其他来源语言查找同一专题；专题原名与已核实别名应参与检索，不能因英文整理生成同一对象的重复专题。
- 用户手动编写和修改的正文保留其所用语言；文件标题统一英文，后续自动更新继续保留人工修正。

## 文件内容与页面

- 文件内容可按需包含概况、重要信息、最近进展、待跟进事项与来源。上述是建议结构，不是每个场景必填的固定字段；没有依据时不生成内容。
- 每次更新能回查原始录音总结及相应版本；不同日期的状态、观点或指标应注明时间。删除或修订来源后，受影响内容须重算或失效。
- 主页面直接展示专题/Markdown 文件列表、搜索、新建与文件阅读/编辑；内容拆分后可显示目录。不用内部候选、不可用、拒绝、只读视图等状态作为一级分类。
- 支持重命名、编辑、移动、合并/拆分及删除。合并/拆分提供可审阅结果，保留来源；用户操作产生的事实不冒充会议原话。
- 必要的新内容确认在对应文件内以来源和更新差异呈现，不额外建立一套状态导航；现有未确认内容的 AI 使用限制继续成立。
- 删除记忆前展示实际影响并执行既有清理机制；原始录音及会议总结保留。

## 验收条件

- R1：当授权总结包含同一持续关注对象或议题的明确相关信息时，系统应将其积累到同一专题，并保留各次会议来源；对象不限于项目。
- R2：当新会议补充已有主题或事件时，系统应更新对应文件并去重；不同时间的变化应保留可追踪记录，不因新增会议生成同义文件。
- R3：当一场会议涉及多个专题时，系统应按相关片段分别关联；同一事件可关联多个专题，不将整篇总结重复复制到每个专题。
- R4：当名称相同但关系依据不足，或内容归属不确定时，系统应保留独立内容或待整理状态，不强行合并，不把业务类型作为身份。
- R5：当用户重命名、移动、合并/拆分或编辑后，后续整理应保持稳定身份与人工修正；并发修改时保留草稿并提示冲突。
- R6：当用户首次查看记忆时，系统应默认展示 Markdown 专题文件，不要求先选择行业、业务类型或记忆状态；搜索覆盖专题名称、别名与可访问正文。
- R7：当专题内容少时，系统应保持单文件；确有清晰独立内容时才建议拆分，不预建空目录、小节或行业模板。
- R8：当自动整理产生未确认的新内容时，系统应在相关文件内提供来源与更新审阅，不扩大未确认信息的 AI 使用权限。
- R9：当记忆被删除或来源被撤回、修订、移出授权范围时，系统应更新相关内容的可用性，保留版本和清理约束。
- R10：当用户更换账号时，系统应隔离文件、搜索、草稿、待审阅更新及缓存；专题名称和文件路径不得成为账号或授权依据。
- R11：当来源包含观点、提议、计划或过往状态时，系统应保留其性质与日期，不能将其自动升级为已决定事项、当前事实或实时行情。
- R12：当系统自动整理记忆时，正文和内部章节应依据实际内容和语境选择语言，不限定中文、英文或混合；所有文件标题统一英文，中文原名保留为别名，逐字引用保持原文。
- R13：当用户以中文原名或已核实别名搜索、引用或补充英文记忆时，系统应关联到同一专题，不因语言不同复制专题，也不自动翻译用户已有手动内容。

## 约束与范围

- 仅整理用户选择并授权的会议。优先使用有效总结；无总结时的转写回退继续遵守已有授权及说明。本机文字上传云端须单独授权，不包含音频上传。
- 本轮是通用分类与 Markdown 体验的需求讨论；不进行桌面发布、线上部署或外部行情查询，不引入课程、CRM 或投资行业各自的完整业务系统。
- 同一份记忆的展示、编辑、检索与对话使用必须一致，不能创建与真实记忆脱节的 Markdown 副本。
- 具体拆分阈值、自动合并策略和实现方案留待技术设计；后续设计需提供可审阅行为与异常处理。
